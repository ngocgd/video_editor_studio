# Phase 11 — Analytics (YouTube Analytics API and Reporting API sync, dashboard, suggestions)

Branch `feat/analytics` (lane e), built on `feat/youtube-channels-upload` (phase 10 part 1, not yet on main). This was a code-only run: Docker was down the whole time, so the host toolchain was used and every Docker-based check is pending.

## What shipped

- **Schema.** Migration `db/migrations/20260927500000_analytics.sql` adds `analytics_tracked_videos`, `video_metrics_daily`, `video_retention`, `channel_metrics_daily`, `analytics_sync_state`, `analytics_reporting_jobs`, `analytics_reporting_reports` and `analytics_suggestions`. Every table carries `tenant_id`, and `scripts/lint-tenant-queries.sh` covers all eight. The queries live in `db/queries/analytics.sql`, and batched upserts pass their rows as jsonb.
- **Google clients** (`api/internal/youtube`, new files only). `AnalyticsClient` covers `reports.query` and the Reporting API calls (report types, jobs, reports, and a capped streamed download that only sends credentials to Google hosts or the configured test host, with the URL scrubbed from errors). `Client.MyChannelStatistics` and `Client.Videos` read the subscriber count and video metadata through the Data API quota ledger.
- **Sync** (`api/internal/analytics`). The Analytics API sync fetches each metric group per channel and per tracked video. It uses a 3-day look-back from the last complete Pacific day and backfills from the publish day for a video that has no history. The channel window covers 365 days for the YPP year. A metric group the API rejects is stored as absent with its reason, never as 0. Retention (100 buckets) falls back to `audienceWatchRatio` alone when `relativeRetentionPerformance` is refused. The reach sync picks `channel_reach_basic_a1` (or a newer version of the same family) from `reportTypes.list`, then adopts or creates the job. It lists reports since its cursor, parses each CSV as a stream (columns mapped by header name, BOM stripped, fields capped, CTR weighted by impressions) and claims the report id in the same transaction as the row upsert, so a report listed twice is not counted twice. A dead grant fails the sync and marks the channel `reconnect_needed`. Failures of the reach report or the channel counter are recorded as notes and do not stop the Analytics API data.
- **Jobs.** The River kinds `analytics.sync` (unique per channel) and `analytics.sync_all` run on a dedicated queue `analytics` with a periodic job at 09:00 Asia/Bangkok. Quota errors snooze until the Pacific reset, and auth errors cancel the job. The worker registers them only when `GOOGLE_CLIENT_ID` is set.
- **Suggestions.** The rules are versioned in code, and each one records its evidence: low CTR (below the channel median over at least 1,000 impressions), weak hook (more than 35% drop by 30s), split long video (8 minutes or longer, with average view percentage below the median) and upload cadence gap. They are recomputed after each sync and can be dismissed.
- **Explain.** The `analytics.explain` pipeline step sends only aggregates to the tenant's configured LLM: 28-day totals, the previous 28 days, YPP progress, and the top 20 videos as ids and numbers, with no titles. It runs in the worker and reports the provider, model and cost. The output is rendered as plain text.
- **API** (`api/internal/analyticsapi`, `openapi/paths/analytics.yaml`). It serves the overview, "Sync now", the video table (server-side sort, opaque cursor), video detail, tracked videos (track by URL or id, checked against the channel with the Data API; untrack for manual videos only), suggestions with dismiss, and explain with its result. Reads need the viewer role and writes need editor. Missing metrics are absent fields with reasons in `unavailable`.
- **Web.** The Analytics page (`/analytics`, `/analytics/videos/$videoId`) has a channel overview with a uPlot trend (lazy chunk), YPP bars, "data through" stamps for both sources and "Sync now". It also has the virtualized video table, video detail with the daily chart, retention curve and impression-weighted CTR, the suggestions panel, Explain and track video. The Dashboard gains channel widgets (28-day views, suggestion count, YPP). Analytics is linked from the nav rail, the command palette and the top bar.
- **Wiring.** `api/cmd/api` embeds the analytics API. `api/cmd/worker` adds the analytics queue and its config, and its netguard hosts cover oauth2, www, youtubeanalytics and youtubereporting.googleapis.com. `deploy/compose.yml` passes the Google client and the quota settings to the worker.

## Verification

Docker was down for the whole run (`docker info` fails). The host toolchain mirrored the Makefile targets.

- gen: the redocly bundle, oapi-codegen, sqlc and the web client were regenerated on the host. This showed drift in the untrack summary (the source was edited after the last regeneration), which was committed as a regeneration. After that, `git diff` is clean. The migrations copy is in sync.
- lint: `go vet ./...` (also with `-tags integration`) passes in api and tools, and `golangci-lint run` reports 0 issues (also with the integration build tag). tenantctx and `scripts/lint-tenant-queries.sh` pass.
- test: `go test ./... -count=1` passes in api and tools (without `-race`: the host has no C compiler). The unit tests cover the rules table, the look-back and backfill math, the PT day, the rejected-group and all-rejected paths against a fake `reports.query` server, the retention fallback, the reach CSV parser (per-video-day aggregation, header drift, unknown columns, empty report, malformed lines, a 100k-row report), the job outcome and schedule, the sort and cursor paging, video id parsing, the explain input (no free text) and routing. `workers-python` was not touched by this branch, and its pytest was not rerun.
- web: `npm run typecheck`, `npm run lint`, `npm test` (19 files, 108 tests), the `npx vite` bundle and `npm run budget-check` pass. The analytics route's first paint is 154.9 KB. The authenticated shell is 165.8 KB, above the 160 KB soft target, as it already was on the base branch.

It needs a real Google OAuth app and a real channel, which are external, and the first reach report arrives about 48h after the reporting job is created. The code path is built and covered against fakes (integration pending).
- Implementation step 1, the live verification of the metric combinations and the reach report type id and columns, and creating the reach job on day 1: **pending** for the same reason. `analytics/querysets.go` and `analytics/reporttypes.go` carry the doc links and say that a live check is outstanding.
- The Dashboard shows YPP progress, and suggestions list their evidence: **built**. Real data is pending as above.
- "Videos awaiting review" on the Dashboard: **not built**. It needs the publications from phase 10 part 2, which have no API yet.
- Performance budgets: the 100k-row CSV parse is a unit test, and the endpoint latencies and the 200-video sync time need the stack and real data (**pending**).
